# Portia

You orchestrate. The `portia` CLI decides everything deterministic; you branch only on its exit codes: exit 0 means go on, exit 10 means nothing to do, exit 11 means stop and show the person the output. Never read meaning into its wording; the only exceptions are the JSON fields and the quoted phrases a step names exactly.

Before anything else, run `portia version`. If the command is not found, or a later command fails with "no profile found", follow the `portia-setup` skill first, then carry on.

Run every command from the root of the target repository checkout this session started in. Portia finds its profile at `PORTIA_PROFILE` (an absolute path), else `portia.config.ts` at the repo root, else `~/.portia/profiles/<repo name>.ts`. Never edit that checkout.

The plan lives in each ticket as a fenced block tagged `plan` (a three-backtick fence opened with the word `plan`). Blocks tagged `portia` on older tickets still parse, but write new ones as `plan`. Branches are `<prefix>/<KEY>`, where the prefix is the profile's `branchPrefix`; the integration branch is `<prefix>/<PARENT>`. Changing `branchPrefix` mid-run orphans that run's branches, so finish or rename them before switching. Nothing Portia writes to the remote or the tracker names the tool, so never add its name to a PR, commit or comment yourself.

**Long commands:** `portia drive`, `portia land`, `portia epic`, `portia gate wave`, `portia gate baseline`, `portia env template`, `portia worker wait`, `portia amend wait` and `portia answers wait` can outlast the Bash tool's 10-minute limit. Run them with the Bash tool's `run_in_background` and its `timeout` set as high as the tool allows, never in the foreground and never chained after another command with `&&` (run that one first, on its own), and act on the exit code when you are notified it finished. A background command can still be stopped at the tool's time limit: when `portia drive` is, run it again at once; the workers it started go on, and the next drive picks up where it stopped. That notification is the only wait: never poll for one with `pgrep`, `ps` or a `sleep` loop (`pgrep -f "portia drive"` matches its own command line, so the loop never ends and holds the session open). Landings for different children may run concurrently.

**Never:** merge to main; widen a permission; guess when unsure (park instead); edit the ledger or the run log by hand; start a worker as a subagent.

**Scripted person.** Before putting any question to the person, run the matching `portia eval-answer`, which answers from the `PORTIA_EVAL_ANSWERS` script of a headless eval run. Exit 10: there is no scripted answer, so ask the person as written. Exit 0: take its answer and ask no one. Exit 11: stop and show the output. `portia drive` asks the script itself at the plan's yes, the questions, the W5 sign-off and a park, so a stop it returns means the script had no answer there: ask the person. Three stops come back though the script has an answer: a `spec-signoff` carrying `coupling`, a `parked` carrying `repeats`, and every `spec-amendment` (below). Which one to run:
- The plan's yes (section 0, step 3): `portia eval-answer plan <PARENT> --from <file>`. It records the sign-off itself; exit 0 goes on to `portia plan write`.
- Which unplanned children to plan (section 0, step 1) and the go (section 1, step 5): `portia eval-answer go <PARENT>`. Exit 0 means plan all of them, and go.
- The questions (section 1, step 3): `portia eval-answer questions <PARENT>`, then `portia questions <PARENT>` again.
- The W5 sign-off at a `spec-signoff` stop, after the reviewer agent's check: `portia eval-answer specs <PARENT>` in place of `portia signoff specs`.
- A spec amendment's sign-off, after the reviewer agent's check: `portia eval-answer specs <PARENT> --amend <KEY>` in place of `portia signoff specs --amend`.
- A `parked` stop: `portia eval-answer parked <KEY> --parent <PARENT> --question "<the question>"`. The `answer` field of its JSON is the person's answer, which goes to `--note-file`.

## 0. Plan

`<PARENT>` is the epic (or story); its children are the tickets.

1. `portia plan context <PARENT> --out <file>`. It is read-only and works before any plan exists. The file holds the parent, the open children to plan (each with its labels, done flag, description, `block` and blockers), the done and excluded children (context only, never planned), `run.started` (children this run has dispatched or landed), the repo's top-level dirs and package dir, the profile's excludeLabels and its gate names. Decide from the file alone:
   - `parent.block` is null: plan.
   - Otherwise, if some open children have a null `block`, show the person that list once and ask which, if any, they want in this run. Plan only for the ones they name.
   - Otherwise go on to section 1.
   - When `run.started` is not empty, a run already exists: only add the unplanned tickets the person named, and never re-plan a child listed in `run.started` (`portia plan write` refuses one). Keep the parent block as it is unless the person asks to change it.
2. Read the tickets and the code they touch, then draft a plan file: `{ "parent": { "block": "…" }, "children": [ { "key": "<KEY>", "block": "…", "needs": ["<NEED>"] } ] }`. The parent block holds `scope:` (the PR title scope) and one `scenario: F1 = Given …, Then …` line per scenario. Each child block holds `wave:`, one `needs: <NEED> # reason` line per need, `touches:` globs, `requirements:` (scenario ids), `evidence:` (the command that proves it), `tier:` (high or standard), `lane:` (light or full) only to override the lane the CLI derives, `size:` XS, S, M or L, no larger than the context file's `maxSize` (anything larger fails the size rule: split the ticket), and, when the ticket links a Figma node or a Claude canvas, `design: <link> route=<path> persona=<name> frames=<frame>,<frame>`, and, on the spine only, one `hook: <file> # <what the stub holds>` line per hook it scaffolds (below). Rules:
   - Never put a plan block on a done ticket. A `needs` may name a done ticket: it counts as satisfied.
   - Tickets carrying any of the profile's excludeLabels are never planned.
   - Same-wave touches must be disjoint: no two children in one wave may touch the same file.
   - Wave 0 is the spine. It owns every shared schema and contract change, and writes every scenario as a failing acceptance spec whose test titles start with `"<id>: "` (for example "F2: …"). It carries one `acceptance: <id> = <path>` line for every scenario. The specs go with the target repo's acceptance specs, where the profile's acceptance step runs them, each inside the touches of the child that owns its scenario (the later child listing it, or the spine when it owns it): for example `specs/<feature>/<id>.accept.ts` beside that child's own specs, never a directory of their own that no ticket declares. The spine lists each spec file in its touches by its exact path, not the owner's whole directory. A shared spec helper goes inside the spine's own touches (its feature's specs directory). The check refuses a spec outside its owner's touches or the spine's.
   - The spine may own a scenario that only it can deliver: when the foundation ticket is the spine and no later ticket delivers one of the scenarios, list that id in the spine's `requirements:`. Its exit gate then runs that scenario, which must pass, while every other spec it writes still fails. Plan it that way rather than adding an extra spine ticket or listing the scenario on a ticket that does not deliver it. Leave off the spine's `requirements:` every scenario a later child lists: a scenario it shares is left to that child, and the check warns.
   - Each child's `needs` array matches its block's `needs:` lines.
   - No child edits a sibling's file. When one scenario's feature plugs into code another child owns, the spine owns the plug-in point: it scaffolds a hook, a stub module both sides use, inside its touches, named on its block as `hook: <file> # <what the stub holds>`. The file sits in the touches of the child whose feature plugs in, which fills it; the other child only calls it. For example, a canyon surcharge added to a delivery's price: pricing (`src/pricing/**`) must not hard-code `surchargeCents = 0` in its own routes, leaving the surcharge child (`src/surcharge/**`) to edit them and park. Instead the spine writes `hook: src/surcharge/rules.ts # surchargeCents(county, priceCents) returns 0`, lists the file in its touches, pricing calls it, and the surcharge child fills in the table. The check warns when two children's tickets meet at a route or file and no hook sits in either's touches.
   - Shared registry files (for example a job or route registry) and new repository files are needed by almost every child. Either the spine scaffolds them, or the plan states a standing rule that each child adds its own lines or new files there; same-wave children never list the registry in touches.
3. Show the person a wave table: wave · key · summary · needs · files touched · scenarios (each need with its reason, files touched as a count), plus a lane column when the context file's `lanes` is true, taken from the `lanes` field of `portia plan write <PARENT> --from <file> --dry-run --json`, and a ripples column: each child's ripple count from the `ripples` field of the same output (the files outside its touches that import a module it touches). A `ripple` warning names a production file outside a child's touches that imports one of its modules: widen that child's touches to hold it, or say why it stays out, before asking for the yes. Then wait for an explicit yes, or for changes; redraft and show it again until they say yes. Never run `portia plan write` without that yes (the one exception is a need the spine's spec review adds, in section 3). On the yes, run `portia signoff plan <PARENT> --from <file>` to record it.
4. `portia plan write <PARENT> --from <file>`. Before writing anything it parses every block, refuses any block that names the tool, and runs the full check on the plan as the tickets would hold it; then it writes the parent block onto <PARENT> and each child's block onto its ticket, and links each need as a blocker. Warnings print and the write goes ahead. Exit 0: go on to section 1. Exit 11 with "was not written": nothing was written; redraft from the findings with the person and show the table again. Exit 11 with "partially written": the tracker failed mid-write; fix the cause and re-run the same file (the write is idempotent), with no redraft.

## 1. Intake

1. `portia permissions` (adds Portia's deny rules to this checkout's local settings; it never adds an allow).
2. `portia check <PARENT>`. Exit 11: show every finding and stop; the plan in Jira must change.
3. `portia questions <PARENT>`. Exit 11 with a JSON array: ask the person every question in it in one round (back-to-back AskUserQuestion calls if there are many), write their answers to a file as `{ "<id>": "<answer>" }`, and run `portia answer <PARENT> --from <file>` until it exits 0. Exit 11 with no JSON: show it and stop. Workers get the answers in their briefs.
4. `portia integration init <PARENT>`, then `portia env template <PARENT>`, then `portia gate baseline <PARENT>`.
5. Publish the plan page (below), then `portia status <PARENT>`. Show it, with every edge and its reason, and the page's link, and wait for the person's go.

**The plan page.** A private page of the plan and its waves, whose link `portia view` shows on the Run page. Run `portia plan page <PARENT> --out <file> --json`, read the file, and publish it unchanged with the Artifact tool (`icon` "map", and `url` set to the JSON's `url` when it is not null, reading that artifact first so the link stays the same). Then `portia plan link <PARENT> <the artifact's link>`. Without an Artifact tool, or when the publish is refused or fails, say so once and go on: the page never holds up a run.

`portia drive` needs `workers.mode: "detached"` in the profile (`workers: { mode: "detached" }`); with any other mode it stops with an error naming that setting. If it is missing, tell the person to set it; never start a worker as a subagent.

## 2. Load designs once (V6)

For each child with a `design:` line, before its wave, one frame at a time:

- Figma: read the frame through the Figma connector (screenshot and design context). Write the PNG and an ElementValues JSON (role, name, color, background, fontFamily, fontSize, fontWeight, lineHeight, padding, radius, width, height per element) to files, then `portia design ingest <KEY> --parent <PARENT> --frame <name> --png <file> --values <file>`.
- Claude canvas: read the artifact with the Artifact tool, save the HTML, then `portia design load-canvas <KEY> --parent <PARENT> --html <file> --frame <name> --width <px>`.

## 3. Drive

`portia drive` takes every deterministic step of the run itself: it records landed children, brings up environments, dispatches, starts and waits on the detached workers, applies their results, decides failures, lands, publishes the ledger, runs the wave gates and the epic gate. It derives its position from the run log each time, so it is safe to run again after any stop or crash. You act only on the stop it names.

1. On a resumed run, publish the plan page first when this session has not (section 1) and the plan changed or `portia plan page` shows no `url`. `portia integration sync <PARENT>` before the first drive, and again before any drive that follows a stop that took the person's time. Exit 11: main conflicts; tell the person and wait (R5). Exit 0 when it merged anything from main: run the typecheck in the integration worktree (`<worktreesDir>/<repo>/<PARENT>`) before driving. Main can break the epic's specs (renamed fields, changed shapes), and a migration from main may need the epic's migration renamed to sort after it; fix, commit and push there.
2. `portia drive <PARENT> --json`, run with `run_in_background`; act on its exit code when you are notified it finished. Drive lands children and waits on workers in the background while it dispatches others, and it stops on anything held for you or the person as soon as nothing but running workers is left: those detached workers go on while you act, so act promptly and drive again, and the next drive picks up what they finished. Exit 0 is epic-ready. Exit 10 is a stop that needs you or the person. Exit 11 is failed or error. The JSON is `{ parent, steps, stop }`; branch on `stop.kind`.
3. Act on the stop, then run `portia drive <PARENT> --json` again:
   - `plan` (exit 10): there is no plan to drive, or it lacks the person's yes. Go to section 0.
   - `questions`: ask the person each one as in section 1, step 3, then drive again.
   - `spec-signoff`: the spine finished and its specs wait. Drive runs the coupling check itself before any sign-off, the script's included, and when it finds one it signs nothing off and puts the entries in the stop's `coupling`. First run `portia plan specs <PARENT> --json` (the same check, so it lists the stop's `coupling`, or none); each entry of its `coupling` array is a scenario whose spec imports a module or requests a route of another child (`other`) that the scenario's owner (`owner`) does not need. Then have a read-only reviewer agent check each acceptance spec in the stop's `specs` against its scenario (every clause asserted, no two scenarios contradicting, no brittle coupling to module paths, no spec depending on behaviour another scenario delivers: when one does, name both scenarios and the child that delivers it; and every assertion satisfiable by a correct implementation on the repo's test runner at its installed version: check the version, and look for runner gotchas such as a matcher that changes the object it checks, like `toMatchObject` with `expect.any()` overwriting the field a later line reads on some bun versions, or an assertion on a value no implementation can produce), handing it the `coupling` entries to confirm or dismiss, and bring its findings to the sign-off. Settle each confirmed dependency before the sign-off, so no child is dispatched before what its specs need has landed. When the owner's scenario text does not require the other feature, decouple the spec: record `portia signoff specs <PARENT> --by reviewer --no --note "Review finding: …"` naming the assertion to drop or loosen (the reviewer's no, not the person's, so it never counts as their decision); drive then starts a fresh spine worker with that note, and this stop comes back when it finishes. When the scenario does require it, add `needs: <other> # its spec needs <the feature>` to the owner's block (moving it to a wave after the other's) and run `portia plan write <PARENT> --from <file>` with the parent block unchanged and that child alone; it refuses a child already started, so decouple that one instead. Show the person every such change at the sign-off. While a coupling is listed, every drive stops here again: once each is settled the list empties and drive applies a scripted sign-off itself; for one the reviewer dismissed, record the sign-off yourself as below (`portia eval-answer specs` in a scripted run). When the reviewer finds any other fault in a spec, the person is not asked either: record it the same way, `--by reviewer --no --note "Review finding: …"` naming the fault, and drive again. Only specs the reviewer passes go on. Then stop for the W5 sign-off before the spine lands: show each acceptance spec and its scenario and ask the person to confirm each test encodes its scenario faithfully and that each test's title starts with its scenario id ("F2: …"; each child's exit gate selects its tests by that prefix). Record their answer with `portia signoff specs <PARENT>`, adding `--no --note "<their notes>"` on a no, and drive again: a yes lands the spine, a no starts a fresh spine worker with their notes. No wave 1 until the spine lands.
   - `spec-amendment`: a child claims its own acceptance spec cannot pass as written (`child`, `path`, `scenario`, `assertion`, `evidence`), and drive does not loop it. Its spec goes back to the spine: when the stop carries no `amendment`, run `portia amend start <KEY> --parent <PARENT>` (a detached amendment worker that may change that one assertion only, every clause of the scenario still asserted; drive starts it itself in detached mode, so the stop usually carries `amendment` already), then `portia amend wait <KEY> --parent <PARENT>` with `run_in_background`. Exit 11: show the reason; when the worker found the spec right after all, answer the child with `portia drive <PARENT> --answer <KEY> --note-file <file>` saying so. Exit 0: have the read-only reviewer agent check its `diff` as for the W5 sign-off (the claim reproduced, only that assertion changed, every clause still asserted, satisfiable on the repo's runner). When the reviewer finds a fault, the person is not asked: record it with `portia signoff specs <PARENT> --amend <KEY> --by reviewer --no --note "Review finding: …"` naming the fault, then `portia amend start` again with the same note in a file as `--note-file`, and review the new diff. Only a diff the reviewer passes goes on: show the person the claim, the evidence and the diff, and record their answer with `portia signoff specs <PARENT> --amend <KEY>` (`--no --note` on a no, then `portia amend start` again with the note as `--note-file`). On a yes, `portia amend land <KEY> --parent <PARENT>` puts it on the integration branch, and drive again: it redispatches the child onto the amended spec. Never edit the spec yourself, and never tell the child to.
   - `parked`: a child asks a question (`child`, `attempt`, `question`). A park that names a sibling (its key, or a file in its touches) never reaches you while that sibling is still running or landing, and once the sibling lands after the child was dispatched, drive sends the child again onto it unasked; a spec claim made before any sibling's landing goes again the same way before an amendment starts. With `repeats`, it has parked that many times running on one head (a rebase onto a sibling's landing does not count as a new head) and drive stopped answering it from the script: do not run `portia eval-answer parked` again. Read the repeated questions and settle the cause yourself (a feature another child delivers: if that child has landed, drive brings the worktree onto it, so answer saying so; if not, wait for it; a spec coupling: decouple the spec), and answer with what changed; when nothing you can change would help, show the person. Otherwise show the person the question as plain text, never with AskUserQuestion, say they can answer here or with `Q` in `portia view`, and run `portia answers wait <PARENT> --since <the JSON's at>` with `run_in_background`. Exit 0: they answered in the view, so drive again. Exit 10: nothing waits any more, so drive again. Stopped at the tool's time limit: run it again with the same `--since`. If they answer here, stop the background wait first, then write their answer to a file and run `portia drive <PARENT> --answer <KEY> --note-file <file>`; it records the answer and drive redispatches the child with it. Every (re)dispatch's `portia env up` rebases the child's worktree onto the integration tip when the tip has moved, so what landed since is in it; a worktree with uncommitted changes or commits that conflict keeps its old base, and its brief says so. It takes an answer for any child drive stopped on for one, including one already answered: the newer answer replaces it. When the park is "touched files outside its Touches" and the person approves those files for this child, first run `portia touches allow <KEY> --parent <PARENT> <glob...> --why "<their reason>"` (`portia touches list` shows them), then answer as above. Never widen the profile's `allowedIncidental` for one ticket. Parked on a rebase conflict in a shared registry file: resolve it in the child's worktree keeping both sides' lines (`git fetch origin`, `git rebase origin/<prefix>/<PARENT>`, fix, `git rebase --continue`), then answer the park saying so; drive lands it again.
   - `failed` (exit 11): drive had no automatic next move. Show the person `child`, `step` and `reason`, and stop. A wave or epic gate failure is theirs to fix on the integration branch; once fixed, drive again. When the child review command failed (`step` land), fix it and drive again: do not redispatch. With `spend` set, a dispatch reached a spend cap (`scope`, `spent`, `cap`): raising it is the person's spend decision, so ask them, and once they have, drive again; an answer the child still needs goes with `--answer` as for `parked`.
   - `error` (exit 11): drive could not go on (a refused setting, every account at its usage limit, GitHub or the tracker). Show the person the message and stop; once it is fixed, drive again.
   - `epic-ready` (exit 0): every child landed and the epic gate passed. Go to section 4.
4. A child that failed is decided by drive itself, retry or park; a park it decided comes back as a `parked` stop. Landing failures caused by CI or GitHub are landed again by drive, and after the third in a row come back as `parked`.
5. At each stop, send the person one message with `portia status <PARENT>` (H4).

## 4. Epic PR

The epic gate already ran inside `portia drive`. Give the person the epic PR's link (`stop.pr`). A person merges it; you never do (R3).
